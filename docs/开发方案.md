## 一、全网调研结论（为什么做、做什么、差异化在哪）

### 1.1 市场格局：三类玩家，无"智能体"成品

| 类型 | 代表 | 能力 | 缺口 |
|------|------|------|------|
| 政府侧信息系统 | 财政部专项债券穿透式监测系统、全口径债务监测平台、预算管理一体化2.0债务模块、发改重大项目库 | 流程填报、数据汇总、限额控制 | **无智能审核**，审核靠人工；填报错误靠上级退回 |
| 中介机构人工服务 | 律所/会计所出具"一案两书"、咨询机构代编实施方案 | 专业判断 | 纯人工、贵、质量参差；无全过程跟踪 |
| 地方委托运维 | 山南市财政局30万/年委托第三方：填报指导+数据审核+债务汇总分析+风险监测+**业务培训** | 全过程人工服务 | 人力密集，难以分县市规模化 |

**结论**：财政部穿透式监测系统解决"数据上报"，但"数据审核、材料审查、问题整改、业务培训"仍在市县财政和第三方服务机构手里，且是人工。审计学会2025年课题清单（多智能体审计框架、审计整改智能体、AI+审计语料治理）证明方向正确但**无成品落地**。本智能体 = 把"第三方全过程服务"智能化，对标用户即是市县财政局、省财政厅处室、会计师事务所/律所/咨询公司。

### 1.2 制度框架已收敛（规则库有权威依据）

- **法律**：《预算法》(2014修订)及实施条例（第43-47条 债务限额/预算/风险预警）
- **国务院**：国发〔2014〕43号（借用管还相统一的总纲）、国办函〔2016〕88号（风险应急处置预案）
- **国办52号文**（国办发〔2024〕52号《关于优化完善地方政府专项债券管理机制的意见》）——当前专项债管理**操作总纲**：
  - 投向领域"负面清单"管理 + 资本金"正面清单"（上限25%→30%）
  - "一案两书"制度 + 实施方案标准化模板
  - "自审自发"试点（10省+雄安，2026年扩至14省+雄安，财债〔2026〕14号）
  - "常态化申报、按季度审核"（10月底集中报下年度，2/5/8月底补充报送，3/6/9/11月采集下发）
  - 专户管理、穿透式监管、偿债备付金制度、资产分类管理
- **财政部系列**：财预154/155号（一般/专项债务预算管理）、财预〔2021〕61号（项目资金绩效管理）、110号（用途调整操作指引）、175号（违规处理处罚机制）、财办预〔2022〕27号（支出进度通报预警）、财预〔2023〕51号（新增限额分配办法）、会计处理暂行规定（投资表/还款表）
- **部委**：自然资发〔2025〕45号（土储债）、厅字〔2019〕33号（配套融资）
- **地方三级**：省（如粤财债〔2021〕7号、河南省债管考核办法）→ 市（如江财债〔2021〕20号）→ 县。**江门市清单证明"国家/省/市"三级分类结构是实务通例**，直接作为法规库目录骨架。

## 二、业务建模

### 2.1 服务对象与主线

- **用户**：市县财政局（被审方兼使用方）、省财政厅（审核方）、第三方服务机构（我们是工具供给方）
- **两条主线**：
  - 项目线：谋划 → 项目库 → 申报审核 → 发行 → 建设 → 运营 → 资产
  - 资金线：额度下达 → 拨付 → 支付 → 收入归集 → 备付金 → 还本付息
- **四环节×智能体能力矩阵**：

| 环节 | 管理内容 | 智能体能力 |
|------|----------|-----------|
| 借 | 项目库建设、申报、额度、发行 | 材料清单核对+负面清单筛查+收益覆盖测算复核+申报报告生成 |
| 用 | 拨付、支付、进度、用途调整 | 支付流水规则扫描+进度预警+用途调整合规指引 |
| 管 | 监测、检查、整改、培训 | 问题台账+整改任务跟踪+咨询问答+二次复核 |
| 还 | 收入、备付金、还本付息、资产 | 收入收缴监测+备付金计提校验+资产登记勾稽+到期提醒 |

### 2.2 核心业务闭环（用户需求1:1映射）

```
分县市审核 → 审核报告生成 → 问题台账 → 培训反馈（高频问题提炼）
    ↑                                    ↓
二次复核 ← 整改结果提交 ← 整改过程咨询 ← 被审单位
    ↓
复核通过 → 项目建档 → 全过程底稿 → 立卷归档
```

### 3.1 七页面（多页线性推进）

1. **首页/总览** — 全市县债务总览、到期提醒、预警汇总
2. **法规库** — 国家/省/市三级树 + FTS5全文检索 + 条款引用跳转 + 版本状态（现行/废止/修订）
3. **项目库** — 项目全生命周期台账 + 材料清单核对（一案两书/四证/可研批复打勾矩阵）+ 申报审核入口
4. **审核工作台** — 按环节（借/用/管/还）选项目→跑规则→逐条问题（引用条款+证据材料）→生成审核报告
5. **问题台账** — 分县市问题列表 + 整改任务状态机（待整改→整改中→待复核→复核通过/退回）+ 整改咨询入口
6. **培训辅导** — 高频问题TOP榜（从台账自动统计）+ 政策问答（RAG法规库）+ 案例库
7. **底稿归档** — 按项目全过程底稿时间线 + 一键立卷导出

### 3.3 审核规则引擎（系统内核）

规则=数据不是代码。每条规则：

```yaml
- no: AP-012
  stage: apply          # 借
  name: 收益覆盖倍数不足
  clause: 国办发〔2024〕52号(四)；财预〔2021〕61号
  severity: P0          # P0=否决项 P1=限期补正 P2=提示
  check: |
    覆盖倍数 = 项目运营期收入现值 / (债券本金+利息)
    倍数 < 1.2 → P0；1.2-1.5 → P1（附敏感性说明）
  evidence: [融资平衡方案, 财务评估报告]
  audit_source: 审计署2025报告：17县虚报预期收益包装121.74亿
```

- **P0/P1/P2 三级**（对齐用户审计交付标准）：P0 否决/重大违规，P1 限期补正，P2 辅导提示
- 每条 finding 强制携带 `clause_ref`（法规条款）+ `evidence`（材料指向）——**AI不编造证据，审核结论必须可溯源**（DAP证据铁律）
- LLM 用途限定：①法规问答 RAG ②材料摘要 ③审核报告文字润色。**审核判定本身走规则引擎，不走LLM**——可解释、可复核、可对抗

### 3.4 培训反馈闭环（用户需求的差异化功能）

- 问题台账自动聚合 → 分县市高频问题 TOP-N → 生成培训讲义（每题：问题描述+涉及项目+依据条款+整改样板）
- 整改过程咨询：法规RAG问答（标注"依据XX条款"），答不准的转人工
- 二次复核：整改材料重跑同规则编号 → 对比首次/复核结论 → 复核报告

## 四、技术选型（Ponytail 最小栈）

| 项 | 选择 | 理由 |
|----|------|------|
| Web | Flask + Jinja2 | 用户既有生态（7Flask路由模式成熟） |
| DB | SQLite WAL + FTS5 | 法规/项目/台账量级（万级）远够；零运维 |
| 规则库 | YAML 文件 | 规则即数据，审计人员可读可维护，无需界面开发 |
| 检索 | SQLite FTS5（jieba分词辅助） | REGKB经验：whoosh/FTS5 万级文档足够 |
| 报告 | Jinja2 模板 → docx（md2docx 内容级格式） | 复用迪源报告管线经验，禁Word COM |
| LLM | deepseek/glm（已有provider链，urllib直连） | 仅问答/摘要/润色；带降级链（REGKB ai_enhancer模式） |
| 端口 | **5210** | 避开 5197/5198/5199/5200/8002/8003 既有项目 |

**明确不做**（YAGNI）：多租户、消息队列、微服务、向量数据库（FTS5先扛，不够再升级）、前端框架（Jinja2+原生JS）、OCR（材料人工上传PDF/扫描件，需要时接入mineru）。

## 六、风险与对策

| 风险 | 对策 |
|------|------|
| 法规更新频繁（52号文后细则陆续出） | 规则YAML与法规库分离，条款引用松耦合；季度巡检任务 |
| 审核结论责任边界（AI不能替人签字） | 所有报告标注"数据预填+待人工复核确认"（底稿铁律）；审核人字段必填 |
| 数据敏感（债务数据保密） | 本地部署单机版，无外传通道；不上云 |
| 与穿透式监测系统关系 | 定位=前置辅导审核工具（事前），不替代监测系统（事后报送）；材料格式对齐监测系统表样（投资表/还款表） |
